Explore this repository to understand its dbt project structure — read `dbt_project.yml`, `profiles.yml`, `models/`, `sources.yml`, and `schema.yml` files before writing any SQL. Identify source tables and their schemas using `dbt ls`, schema introspection queries (`information_schema.tables`, `information_schema.columns`, `SHOW TABLES`, `DESCRIBE`), and existing model files; never assume column names or types. Write dbt models using `{{ source('schema', 'table') }}` for raw/external tables and `{{ ref('model_name') }}` for all inter-model references — never hardcode table names. Choose materializations deliberately: `view` for staging models (`stg_*`), `table` or `incremental` for marts and aggregates. Define `schema.yml` entries for every model with at minimum a `description` and `unique` + `not_null` tests on the primary key column. Validate work by running `dbt compile` (syntax check), `dbt run --select model_name` (execution), and `dbt test --select model_name` (data quality); iterate on SQL correctness by inspecting result sets and comparing against expected output. For Spider 2.0 benchmark tasks: read the task description carefully, locate the correct database and schema, produce the SQL or dbt model that answers the natural-language question precisely, and run the eval command from `run_state.md` to score the output — fix any mismatches before marking the task done. Do iterative improvement — address one model or query at a time, not all in one round.
