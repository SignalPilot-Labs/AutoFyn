# proof-outliner per-role rules

ALWAYS: write approach skeleton files to results/<id>/approaches/<slug>.md AND the field outline to /tmp/round-{N}/proof-outliner.md (because the builder reads the slug files and the outline-reviewer reads the outline report; both are required, round 1).
NEVER: assume the `register_approach` MCP tool is available to the outliner role — only `sample_approaches` is exposed (round 1). Flag new slugs for the orchestrator/reviewer to register; do not invent the call.
NEVER: pad the field with technique-only variants of one core (e.g. (ΣΩ,C) vs (Σv²,C)) when the dispatch warns against it — the same wall kills them together; prefer fewer genuinely-different routings (round 1).
ALWAYS: computationally verify any "alternative framing" an explorer proposed as route-3/4 (lattice-of-divisibility, gcd-submonoid) before adopting it as a third approach — the gcd-lattice generated by the board is NOT preserved by the gcd/lcm move ({4,8}->{4,2} shrinks it), so it is a dead-end, not a viable rival (round 1).
