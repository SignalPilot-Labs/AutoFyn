# outline-reviewer — per-role rules

ALWAYS: numerically re-verify any "triangle similarity" claim an explorer makes (compute all three side ratios AB/AC, AK/AL, BK/CL and confirm they match) BEFORE letting the outliner build a chase on it — the spiral-isogonal explorer reported three spurious similarities (△ABK∼△ACL, △LBK∼△LNC, △LCK∼△BMK) as true because numpy's arccos picks the supplement of obtuse angles, creating fake "angle matches"; on the verified IMO-2026-02 config ALL THREE were false (ratios 1.265/1.114/2.746 etc.) and isogonality ∠BAK=∠CAL was false (10.25°≠4.14°). The TRAP flag "spiral at A does not send K→L" actually extends to all three similarities, not just the one at A. (round 1, imo-2026-02)

ALWAYS: for any analytic "ideal membership" certificate proposed by an outliner, run BOTH (a) Gröbner remainder of the target mod the proposed ideal AND (b) Rabinowitsch `<generators, z·target−1>` reducing 1 — the 4-var ideal membership was dead, the 2-var ideal membership ALSO failed (nonzero remainder), AND radical membership failed (Rabinowitsch returns 1), yet the cleared target Q vanished on all 40/40 sampled REAL common zeros. So a real-variety vanishing can hold with NO ideal/radical certificate — the only rigorous path is a real-arc parametrisation or Real-Nullstellensatz. Do not let a builder claim "P ∈ ideal ⟹ done" without the remainder check. (round 1, imo-2026-02)

ALWAYS: when a prior round's approach file records a polynomial identity as FALSE (with an explicit counterexample), do NOT trust the prior verdict — rebuild e1,e2,e3,Q from the cross/dot tangent form (†) from scratch in sympy and re-run the field division `sp.div(Poly(LHS, ly, domain=QQ.frac_field(...)), Poly(D0, ly, domain=...))`. Round-2 of imo-2026-02: the round-1 approach file's "saturation identity FALSE" verdict (with counterexample Q=256) was itself an arithmetic slip (correct Q=320/3); the from-scratch field division returns remainder 0 with explicit G linear in t. The prior round's source-of-truth file can be wrong; verify load-bearing polynomial claims independently before down-ranking or cutting. (round 2, imo-2026-02)

ALWAYS: when re-verifying a "counterexample" to a polynomial identity, recompute EVERY substituted value from scratch — do not trust the prior round's printed numerics. Round-2: recomputing Q from the cleared-target formula at the round-1 counterexample point gave 320/3, not the 256 the round-1 file printed; the whole FALSE verdict collapsed on that single arithmetic slip. (round 2, imo-2026-02)

NEVER: trust a prior round's claim that it "ran the field-domain Poly(...,domain=QQ.frac_field(...)) check and got nonzero" without re-running it yourself. Round-1's imo-2026-02 approach file claims exactly this for the saturation identity, and the independent round-2 rebuild returns remainder 0. The prior field-domain run was likely contaminated by the same wrong Q value or reduced the wrong expression. (round 2, imo-2026-02)

ALWAYS: when a scout/outliner proposes a sequential-univariate field-division certificate (sp.div over QQ.frac_field), independently re-run the probe script AND verify the divisor leading coefficients are generically nonzero (one numeric eval suffices) — the field-division is genuine only when the divisor's leading coeff is a unit over the field; otherwise sp.div silently does a pseudo-remainder and "remainder 0" does NOT imply field-remainder 0. Round-3 imo-2026-02 antipode: reproduced remainder 0 in 82.8 s and printed both leading coeffs (both generically nonzero), confirming the certificate. Also flag that the step-1 remainder is expected to be NONZERO (degree 3 here) — the certificate requires BOTH divisions, not just the first. (round 3, imo-2026-02)

ALWAYS: when ranking a SOLVED-problem population that still has live `partial` synthetic rivals, anchor the comparison to the last *reviewer* outcome, not the scout's verification — a scout-verified-sound revision (e.g. antipode remainder 0) is still `partial` until the builder actually closes it AND the reviewer APPROVEs; do not let a scout's "verified viable" bump a `partial` approach above a reviewer-APPROVE `solved` sibling in the same round. (round 3, imo-2026-02)

NEVER: let a builder run a "mechanical symbolic verification" sub-step (9b) with GUESSED signs because the sign-pinning sub-step (9a) stalled — that is the documented numpy-sign-trap manifesting as a half-baked certificate. The correct routing is CHANGES REQUESTED → deferral (the framing is sound, the gap is hard), NOT forcing 9b with unresolved signs and NOT RETHINK. (round 3, imo-2026-02 power-secant-product)
